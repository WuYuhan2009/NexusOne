Realtime Voice Architecture

文字与语音几乎同时生成的实时角色方案

目标：降低首字延迟、首音延迟和口播断裂感，同时保持角色人设、系统提示词和刚刚生成效果的一致性。

推荐方案 配置建议 角色边界

首选

方案 A：端到端 Realtime 语音模型

如果要“文字和语音几乎同时生成”，不要再走 LLM 完整出字 → TTS 再合成 的串行链路。首选使用原生多模态实时模型，让同一个会话同时输出文本流和音频流。

低延迟音频边生成边播放
一致性同一 system prompt 约束文本和语音
可打断支持 VAD / barge-in

三种可选架构对比

A. Realtime Speech-to-Speech

模型直接理解/生成音频，并同步给前端文本转写或字幕流。适合直播聊天、陪伴式角色、实时对话。

  • 首音最快，断句最自然。
  • 角色语气写在会话 instructions/system prompt 中。
  • 适合 LiliMu 这类高互动角色。

B. Streaming LLM + Streaming TTS

LLM token 流分句送入 TTS，前端缓冲 1～2 个短句播放。适合必须精确控制文案的场景。

  • 比串行快，但会有切句和拼接成本。
  • TTS instructions 仍有意义。
  • 适合旁白、公告、固定剧本。

C. 先文本后整段 TTS

等文本完全生成后再一次性合成语音。实现简单但不适合“实时几乎同时”。

  • 延迟最高。
  • 效果稳定但等待感强。
  • 只建议用于非实时导出。

config 里还需要写 TTS 提示词吗？

如果改成端到端 Realtime 语音模型：通常可以删除独立 ttsPrompt，把角色说话方式合并进统一的 system / instructions。

保留独立 TTS 提示词只适用于 B/C 两种链式方案，因为那时 TTS 是单独模型，需要额外知道“怎么念”。

// 推荐：Realtime 统一配置
const realtimeSession = {
  model: "gpt-realtime",
  outputModalities: ["text", "audio"],
  voice: "marin",
  instructions: PERSONA_PROMPTS.lilimu
};

// 可删：仅链式 TTS 才需要
// ttsPrompt: "用可爱萝莉声线念出来..."

保证速度与效果的工程策略

1WebRTC 直连浏览器实时音频优先 WebRTC；服务端场景再用 WebSocket。
2双流输出同时订阅 text delta 和 audio delta，字幕不等音频，音频不等全文。
3小缓冲播放前端维护 100～300ms 音频 jitter buffer，避免卡顿。
4VAD + 打断检测用户开口后立刻停止当前播报，清空待播缓冲。
5提示词收敛人设写清楚但不要过长，避免模型每轮重新推理大量无关设定。

角色 Prompt 合并建议

LiliMu（小魅魔 / 可爱萝莉风）

建议定位为成年虚构角色，外在风格是娇小、可爱、撒娇、俏皮的小恶魔感；避免任何未成年性化表达。语音风格写入统一 system prompt：轻快、甜软、调皮、亲昵但保持安全边界。

Guoge（油腻变态下头男）

可以保留“油腻、夸张、自恋、下头”的喜剧标签，但建议明确：不骚扰真实用户、不输出露骨性内容、不攻击现实群体。语音风格：拖腔、浮夸、过度自信、喜剧化。

迁移结论

  • 要最快：用 Realtime 端到端音频，不要等全文后再 TTS。
  • 要“刚刚生成效果”稳定：把角色、口癖、边界、输出格式都放入同一个 system / instructions。
  • 若已使用实时语音模型：config 中的独立 ttsPrompt 可以删除，避免和 system prompt 冲突。
  • 若仍使用链式 TTS：保留 ttsPrompt，但要从“人设设定”改成“朗读风格参数”。
